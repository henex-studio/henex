# HENEX Case Study Voice and Narrative Rules

Date: 2026-06-06
Project: HENEX Website
Use: Reusable writing guidance for future HENEX case studies

## Purpose

This document defines the preferred case study voice for the HENEX website. It should be used when writing or revising UX, service design, design system and future architecture case studies.

The goal is to make each case study sound like the designer is explaining their own thinking, while still keeping the writing professional, concise and suitable for a public portfolio.

## Core Voice Principle

Write like a knowledgeable designer explaining the project in an interview.

The case study should not sound like a third-party project report. It should also not sound like a personal diary. The best balance is a professional first-person voice with clear reasoning, evidence and reflection.

## First-Person Balance

Use first person when the sentence explains a judgement, decision, framing choice or reflection.

Use neutral voice when the sentence explains facts, project context, process steps or system behaviour.

### Use first person for judgement

Good examples:

- I treated the project as a system reconstruction task, not a visual redesign.
- I chose these components because they carry the core user journey.
- I made a deliberate scope decision to keep the project focused.
- I wanted the microsite to work as a handoff tool, not only a visual presentation.
- For me, the main value was the thinking process behind the output.

### Use neutral voice for facts

Good examples:

- The audit revealed mixed navigation patterns and inconsistent search styles.
- The final outcome was a structured design system microsite in Figma.
- The system documented foundations, component anatomy and usage guidelines.
- The project followed four phases: Discover, Define, Develop and Deliver.

### Avoid overusing first person

Avoid repeating “I” at the start of every sentence. This makes the writing feel like a diary or reflection essay.

Weak example:

- I audited the website. I found inconsistencies. I created principles. I built components. I learned about variables.

Better example:

- I audited the website to identify repeated inconsistencies. The findings were then translated into principles, component scope and documentation rules.

## Critical Thinking Requirement

Every major case study section should explain at least one of the following:

1. Why this work mattered.
2. Why this decision was made.
3. What changed because of this work.
4. How the decision influenced the next step.
5. What tradeoff or constraint shaped the outcome.

The case study should not only show outputs. It should connect outputs to reasoning and impact.

## Preferred Section Logic

Each case study should follow a clear narrative chain.

Recommended logic:

1. Context, what the project was about.
2. Problem, what was unclear, broken or fragmented.
3. Solution, what direction was chosen.
4. Outcome, what was produced and why it mattered.
5. Process, how the work developed.
6. Key decisions, why specific choices were made.
7. Evidence, what supports the decisions.
8. Impact, what the work enabled.
9. Reflection, what was learned or would be improved.
10. HENEX Method Recipe, how the project connects to the HENEX framework.

For some portfolio pages, Outcome can appear near the top if the reader needs to understand the result quickly. For NDS, the preferred order is Problem, Solution, Outcome, then detailed process.

## Influence and Impact Writing

Use short impact statements to connect sections. These can be called Influence, System Impact, Design Impact, Interaction Impact or What This Enabled depending on the project type.

Good examples:

- This changed the project framing from “what looks inconsistent?” to “what decision rules are missing?”
- The principles became filters for deciding what to simplify, what to keep and what needed clearer documentation.
- The component work connected abstract design rules back to actual user behaviour.
- The audit turned surface-level inconsistency into a clearer system problem.

## Scope and Tradeoff Writing

Case studies should show that scope was managed intentionally.

Good examples:

- I did not try to document every possible component. I focused on the components that carried the main user journey.
- The project needed to balance visual completeness with clear documentation.
- The decision to limit scope helped keep the case focused and easier to understand.

## Token and System Claims

Do not overstate design system maturity.

If a project created foundations but not a full production-ready token library, describe it as a token-ready foundation.

Preferred wording:

- The original assignment did not produce a complete production token library.
- For this portfolio case study, I describe the work as a token-ready foundation.
- The system had the logic needed for tokens, and later token work helped express this foundation more clearly.

Avoid:

- I built a complete production token system.
- The project delivered a full enterprise-level design system.

Only make strong claims when the evidence exists.

## Tone Rules

1. Use clear English suitable for IELTS 6.5 to 7.
2. Use active voice where possible.
3. Avoid filler openings.
4. Avoid academic over-explanation.
5. Avoid overly emotional language.
6. Avoid long chains of abstract nouns.
7. Prefer short paragraphs.
8. Use bullet points only when they improve scanning.
9. Keep the designer’s thinking visible.
10. Make the link between decision and impact explicit.

## Words and Phrases to Prefer

Use:

- I treated the project as...
- I chose...
- I focused on...
- I made a deliberate scope decision...
- This changed the framing...
- This helped connect...
- The audit revealed...
- The outcome enabled...
- The system translated...
- The work moved from... to...

Avoid overusing:

- The project aims to...
- It can be seen that...
- This demonstrates that...
- Various aspects of...
- A comprehensive range of...
- In order to...

## HENEX Lens Rule

Every formal UX or service design case study should include HENEX Lens in the project meta section, aligned with the ASH template.

The HENEX Lens should include:

1. Primary recipe name.
2. Recipe number.
3. Three HENEX nodes.
4. A short explanation later in the HENEX Method Recipe section.

Example:

- R17 · Make It Tangible Model
- Perception × Meaning × Matter

## Course Project Feedback Rule

For course projects, feedback can be included as an optional section when it adds credibility.

Use feedback when it supports the case study’s design value, such as clarity, communication, system thinking or component quality.

Do not include too many quotes. Two or three short quotes are enough.

## Image and Evidence Rule

Images should support the reasoning, not replace the reasoning.

Use HTML and CSS modules for content that needs to be read, scanned or understood as system logic.

Use images for:

1. Process diagrams.
2. Figma evidence.
3. Complex component anatomy.
4. Final outcome previews.
5. Visual proof of work.

Do not rely on images for essential text, especially on mobile.

## Revision Rule

When revising tone, preserve the confirmed structure unless a structure change is explicitly requested.

If the writing feels too third-person, add first person to judgement and reflection sentences.

If the writing feels too personal, convert factual process sentences back to neutral voice.

The target balance is:

- Personal enough to show thinking.
- Professional enough to support portfolio credibility.
- Concise enough for quick review.
